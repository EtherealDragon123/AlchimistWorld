# 03. Архитектура и формат данных

## 1. Стек

| Что | Чем | Зачем |

## 2. Слои

Главное требование: **GUI можно выкинуть и написать заново, не трогая логику** (NFR-1).

```
┌─────────────────────────────────────────────┐
│ ui_qt/        (PySide6)   ← заменяемый слой  │
│ cli/          (консоль, отладка, импорт)     │
└──────────────┬──────────────────────────────┘
               │ вызывает только services
┌──────────────▼──────────────────────────────┐
│ services/   сценарии: каталог, инвентарь,    │
│             варка, журнал, обмен, настройки  │
│             + шина событий                    │
└───────┬───────────────────────┬─────────────┘
        │                       │
┌───────▼────────┐     ┌────────▼────────────┐
│ core/          │◄────│ storage/            │
│ модели, правила│     │ JSON/TOML, миграции │
│ подбор         │     │ пути                │
│ (без I/O, Qt)  │     └─────────────────────┘
└────────────────┘
```

Правила зависимостей (проверяются `import-linter` в CI и перед коммитом):

| Слой | Может импортировать | Не может |
|---|---|---|
| `core` | только стандартную библиотеку | всё остальное |
| `storage` | `core` | `services`, `ui_*`, Qt |
| `services` | `core`, `storage` | `ui_*`, Qt |
| `ui_qt`, `cli` | `services`, `core` (только модели и enum'ы для отображения) | `storage` напрямую |

Как это помогает сменить GUI:
- Сервисы возвращают обычные dataclass-объекты, а не Qt-модели.
- Ошибки и предупреждения ядра — это **коды с параметрами** (`WarningCode.RARITY_UNITS_MISMATCH, expected=3, actual=2`), а не готовый текст. Текст по коду собирает общий модуль `i18n`, которым пользуется любой интерфейс.
- Об изменениях данных сервисы сообщают через свою шину событий (`CatalogChanged`, `InventoryChanged`, `JournalChanged`) на обычных Python-колбэках. В `ui_qt` есть тонкий мост, который превращает их в Qt-сигналы.
- Новый GUI = новая папка `ui_<что-то>/`, которая вызывает те же сервисы.

## 4. Модель предметной области (`core`)

### 4.1 Элементы

```python
class Element(StrEnum):
    FIRE = "fire"; WATER = "water"; AIR = "air"; EARTH = "earth"
    LIGHT = "light"; DARK = "dark"; MAGIC = "magic"

@dataclass(frozen=True, slots=True)
class ElementVector:
    """Мультимножество элементов: 7 неотрицательных целых в фиксированном порядке."""
    counts: tuple[int, int, int, int, int, int, int]

    total: int                      # сумма единиц
    def __add__(self, o) -> "ElementVector"
    def __sub__(self, o) -> "ElementVector"   # может дать отрицательные — для расчёта недостачи
    def fits_in(self, o) -> bool    # покомпонентно ≤
    @classmethod
    def from_dict(cls, d: dict[str, int]) -> "ElementVector"
    def to_dict(self) -> dict[str, int]       # без нулей: {"fire": 2}
```

Вектор неизменяемый и хешируемый, поэтому годится ключом словаря: на этом держатся индекс рецептов и поиск по журналу.

### 4.2 Сущности

```python
class Rarity(IntEnum): COMMON=1; UNCOMMON=2; RARE=3; EPIC=4; LEGENDARY=5
class BaseType(StrEnum): LIQUID="liquid"; VISCOUS="viscous"; EXPLOSIVE="explosive"
class IngredientCategory(StrEnum): HERB="herb"; PLANT="plant"; ESSENCE="essence"; CREATURE="creature"; OTHER="other"
class PotionKind(StrEnum): POTION="potion"; POISON="poison"; OIL="oil"; BOMB="bomb"
class Kit(StrEnum): ALCHEMIST="alchemist"; HERBALIST="herbalist"; POISONER="poisoner"

@dataclass
class Ingredient:
    id: str; name: str; rarity: Rarity; category: IngredientCategory
    is_herb: bool; elements: ElementVector
    habitats: list[str]; description: str; hidden: bool = False

@dataclass
class Recipe:
    bases: frozenset[BaseType]          # «Любая» = все три
    elements: ElementVector
    required_base_id: str | None = None # на будущее (П-4.4)

@dataclass
class Potion:
    id: str; name: str; rarity: Rarity; kind: PotionKind
    family: str | None; tags: set[str]  # {"black_market"}
    description_md: str
    recipe: Recipe | None               # None = неизвестен
    recipe_note: str | None             # «3+ случайных реагента с провалом» и т.п.
```

### 4.3 Наборы (`rules.py`)

```python
KIT_BASES   = {ALCHEMIST: {все}, HERBALIST: {LIQUID, VISCOUS}, POISONER: {все}}
def kit_allows_ingredient(kit, ing) -> bool   # HERBALIST → ing.is_herb
def kit_allows_potion(kit, potion) -> bool    # POISONER → potion.kind == POISON
```

Если выбрано несколько наборов, подбор выполняется **для каждого набора отдельно**, а результаты объединяются. Вариант допустим, если хотя бы один набор разрешает всё сразу: основу, зелье и каждый реагент. Смешать в одной варке травы по праву травника и эссенцию по праву отравителя нельзя.

## 5. Алгоритм подбора

### 5.1 Точные комбинации (`find_combinations`)

Вход: целевой вектор `T` (из рецепта, `T.total ≤ 6`), список реагентов из инвентаря `(ingredient, vector, qty)`, уже отфильтрованный по набору.

1. **Отсев.** Реагент может участвовать, только если `vector.fits_in(T)`. Все числа неотрицательные, а совпадение нужно точное, поэтому реагент с «лишним» элементом не подойдёт ни в какой комбинации.
2. **Классы.** Реагенты с одинаковым вектором объединяются в класс (Сопли тролля, Мертвостой и Пастушье мыло — все `{Вода×1}`). У класса общее количество `Q = Σ qty`. Так перебор не раздувается от взаимозаменяемых трав.
3. **Перебор в глубину** по классам в фиксированном порядке. Для класса `k` берём `c` от `min(Q_k, ⌊остаток/вектор⌋)` до 0, вычитаем `c·v_k` из остатка. Ветка отсекается, как только остаток уходит в минус. Если остаток равен 0 — найдена комбинация.
4. **Раскрытие.** Комбинация классов превращается в конкретные реагенты: внутри класса по умолчанию сначала берутся самые многочисленные. В диалоге варки внутри класса реагенты можно поменять.

Сложность: глубина не больше 6 (каждый реагент даёт хотя бы 1 единицу, в рецепте их не больше 6), поэтому перебор мгновенный даже при сотнях реагентов.

Один и тот же набор реагентов могут разрешать несколько наборов инструментов, и основы у них разные (П-6.3). В списке это **один** вариант, а его основы — объединение того, что разрешает каждый: иначе порядок наборов в настройках менял бы результат. Оценка «повторов» берётся у того набора, которому видно больше запасов, — у травника класс собран только из трав, и число занижено.

### 5.2 Сортировка вариантов (FR-5.2)

Стоимость варианта = `Σ c_i · w(rarity_i)`, где `w = {1:1, 2:3, 3:9, 4:27, 5:81}`: редкие реагенты тратятся неохотно. При равной стоимости выше тот вариант, где меньше реагентов, потом — где больше останется в запасе.

### 5.3 Сколько раз можно повторить (FR-5.3)

Для одного варианта: `min по классам ⌊Q_класса / c_класса⌋`. Общий максимум зелья с учётом разных вариантов считается жадно: взять самый дешёвый вариант, вычесть, повторить. Это не всегда точный максимум (точный — задача целочисленного программирования), но для подсказки «×3» этого достаточно.

### 5.4 «Почти готово» (FR-6.1, FR-6.2)

1. Тем же перебором ищем подмножество `S` инвентаря, у которого `sum(S).fits_in(T)` и `sum(S).total` максимальна. Среди равных выбираем более дешёвое.
2. Недостача `D = T − sum(S)`.
3. Чем закрыть: запускаем `find_combinations(D)` по **всему справочнику** с бесконечным количеством, не больше 2 реагентов, показываем 3 лучших.

### 5.5 Индекс рецептов и проверка конфликтов (П-5.6)

```python
RecipeKey = tuple[BaseType, ElementVector]
index: dict[RecipeKey, set[potion_id]]
```

Рецепт с несколькими основами занимает несколько ключей. Конфликт — ключ, в котором больше одного зелья. Индекс перестраивается при каждом изменении каталога: при сотнях зелий это микросекунды. Тот же приём (`key → записи журнала`) даёт подсказку «уже пробовали» (П-7.6).

### 5.6 Дистилляция (`core/distill.py`, П-9)

Перебора здесь нет: разбор считается напрямую.

1. Всё положенное складывается в один вектор `E` (П-9.4: эссенции ничем не отличаются от прочих реагентов).
2. Особый случай П-9.5: в экстракте ровно один предмет, он эссенция уровня ≥ 2 → результат `level` фосфорицирующих эссенций той же стихии, и дальше ничего не считается.
3. Иначе каждая стихия `E[element]` дробится жадно: `divmod(units, 5)` даёт столько сияющих и остаток одной эссенцией. Жадность и есть правило (П-9.2): 7 → `[5, 2]`, а не `[4, 3]`.
4. Результат сравнивается со входом: совпал — разбор бессмыслен (П-9.7).

Уровень эссенции читается прямо из её элементов: по П-3.2 единиц в реагенте ровно столько, какова редкость, так что отдельного поля не нужно. Пару «стихия + уровень» в конкретный реагент справочника превращает уже `services/distilling.py` — `core` о справочнике не знает.

### 6.2 Правила записи

- UTF-8, `ensure_ascii=False`, отступ 2, ключи в стабильном порядке, чтобы в git были чистые диффы.
- Атомарно: пишем `файл.tmp` → `fsync` → `os.replace`. Перед заменой старый файл копируется в `файл.bak`.
- Варка меняет два файла (инвентарь и журнал). Сначала готовятся оба `.tmp`, потом подряд два `os.replace`. Если сбой всё-таки случился между ними, в записи журнала хватает данных, чтобы восстановить инвентарь.
- Повреждённый файл не роняет приложение (NFR-8): показывается ошибка с путём и номером строки, предлагается откатиться на `.bak`.

### 6.9 Файл обмена справочником (FR-10.2)

```json
{
  "format": "alchimist-catalog",
  "schema_version": 1,
  "exported_at": "2026-09-11T22:00:00+04:00",
  "exported_by": "Имя персонажа",
  "ingredients": [ … как в 6.3 … ],
  "potions":     [ … как в 6.4 … ]
}
```

Слияние (FR-10.3) идёт по `id`:
- записи с новым `id` добавляются;
- если запись совпадает до байта, ничего не делается;
- если отличается, показывается сравнение по полям (и `updated_at` обеих сторон), игрок выбирает «моё» или «чужое». Можно для всех сразу.

### 6.10 Идентификаторы

`id` — транслитерированный slug названия (`Могильная Лоза` → `mogilnaya-loza`). При совпадении добавляется суффикс `-2`. **При переименовании `id` не меняется.** Справочник переходит от игрока к игроку файлом обмена (§6.9) вместе с `id`, поэтому при слиянии записи сопоставляются правильно, даже если их потом переименовали.

### 6.11 Миграции

`migrations.py` хранит цепочку функций `v1 → v2 → …`. При загрузке файл с меньшей `schema_version` прогоняется по цепочке, а исходник сохраняется как `файл.v1.bak`.

## 7. Импорт из Obsidian (удалён)

Первоначально справочник один раз собирался из Obsidian-заметок кампании (FR-10.1).
Эту задачу импорт выполнил и из приложения убран: теперь справочник ведётся в самом приложении,
а между игроками передаётся файлом обмена (§6.9). Номер раздела оставлен, чтобы не сбить ссылки
на §8–§10.

Справочник кампании, собранный тем импортом, выгружен в `tests/alchimist-catalog.json`: на нём
идут сценарные тесты (§9).

## 8. Локализация

- Все строки интерфейса и тексты по кодам предупреждений — через `alchimist.i18n._()` (gettext). Каталоги `.po` лежат в `src/alchimist/i18n/locale/`.
- Стандартные строки Qt (кнопки диалогов «OK/Cancel») переводятся штатным `QTranslator` с системными `.qm`.

Оформление (FR-9.5) живёт в `ui_qt/theme.py` и в ядро не протекает: там описаны две палитры,
а `apply_theme()` ставит `QPalette` и таблицу стилей. Виджеты, которые кешируют цвета в картинках
или в готовом HTML, пересобирают их по сигналу `on_theme_changed`.
- Данные справочника (названия, описания) — это данные, а не интерфейс. Они не переводятся.
- Исходный язык строк в коде — русский. Для английского (FR-11.4) добавится `en/LC_MESSAGES/alchimist.po`.

## 9. Тестирование

Обязательные тесты ядра (на реальных данных кампании):

| Тест | Ожидание |
|---|---|
| Сумма и точное совпадение | Щёлкорех×2 → `{fire:2}` → Алхимический Огонь на любой основе |
| Одна эссенция вместо двух трав | Тусклая эссенция огня → Алхимический Огонь |
| Лишний элемент | Кровь дракочерепахи ≠ `{fire:2}` |
| Основа различает | `{earth:1, fire:1}`: жидкая → Сила Огра, взрывная → Динамит |
| Коллизия | добавить второй рецепт `(liquid, {earth:2})` → предупреждение с «Зелье Лазанья» |
| Редкость ↔ единицы | необычное зелье с рецептом из 2 единиц → предупреждение |
| Травник | эссенции исключены, взрывная основа исключена |
| Отравитель | только зелья с kind=poison |
| Несколько наборов | травник + отравитель не смешиваются в одной варке |
| «Почти готово» | есть Щёлкорех×2, рецепт Пламя Саламандры (вязкая, `{fire:2, light:1}`) → не хватает `{light:1}`, подсказки: Свечная Роза, Мыльная Трава, Фосфорицирующая эссенция света |
| Варка | списание, добавление зелья, запись журнала; отмена возвращает всё как было |
| Сценарии С-1…С-9 | на справочнике кампании `tests/alchimist-catalog.json`: 63 реагента, 139 зелий, 25 рецептов |
| Миграции и повреждённые файлы | загрузка `.bak`, понятная ошибка |

## 10. Сборка и распространение

| Платформа | Способ |
|---|---|
| Все (для разработки) | `uv run alchimist-gui` или `pip install -e .` |
| Arch, CachyOS, Manjaro | `packaging/PKGBUILD` → `makepkg -si`. Ставится через pacman, Qt берётся системный, пакет весит килобайты |
| Любой Linux | `pipx install .` либо самодостаточная сборка `python packaging/build.py` |
| Windows | PyInstaller → папка с `AlchimistWorld.exe` в zip и вариант из одного файла. С Linux собирается через Wine (`packaging/build-windows-wine.sh`) |
| macOS | PyInstaller → `AlchimistWorld.app`. Без подписи Apple первый запуск — через «Открыть» в контекстном меню |

Одна команда на все ОС — `python packaging/build.py [--onefile]`: она собирает каталоги
перевода, запускает PyInstaller по общему `alchimist.spec` и упаковывает результат.
Библиотеки Visual C++ попадают в Windows-сборку сами, отдельно ставить их не нужно.
Подробности — в [packaging/README.md](../packaging/README.md).

Сборки под три ОС делаются в GitHub Actions (матрица `ubuntu-latest`, `windows-latest`, `macos-latest`) по тегу `v*`: PyInstaller не умеет собирать под чужую ОС.

Точки входа в `pyproject.toml`:

```toml
[project.scripts]
alchimist = "alchimist.cli.__main__:main"

[project.gui-scripts]
alchimist-gui = "alchimist.ui_qt.app:main"
```
